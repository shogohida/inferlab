# inferlab

Go言語だけでゼロから実装したTransformer推論エンジン。PyTorchもONNX Runtimeも、
何かへのcgoバインディングも一切使っていません。フォワードパス（RMSNorm・
RoPE回転位置埋め込み・グループドクエリ因果的アテンション・SwiGLU）、KVキャッシュ、
int8重みオンリー量子化、そしてデコード時のみのcontinuous batchingスケジューラを、
すべて[Andrej Karpathy氏のllama2.c](https://github.com/karpathy/llama2.c)の
ファイル形式と`stories15M`（TinyStoriesで学習した小型のLlama-2アーキテクチャ
モデルで、無料枠のCPUでも1トークンずつ実行できるサイズ）チェックポイントの上に
構築しています。

```
inferlab/
├── internal/tensor/      MatMul・RMSNorm・Softmax・SiLU、int8量子化QuantizedTensor
├── internal/loader/      llama2.cチェックポイント形式のパーサー
├── internal/tokenizer/   llama2.cのtokenizer.bin形式 + BPEマージのエンコード/デコード
├── internal/model/       Transformerフォワードパス本体（Step, StepBatch）
├── internal/cache/       シーケンスごとのKVキャッシュ
├── internal/quant/       int8重みオンリー量子化
├── internal/batch/       デコード時のみのcontinuous batchingスケジューラ
├── internal/api/         /api/generate（SSE）と/api/benchmark
├── web/                  組み込みフロントエンド：生成デモとベンチマークのバーグラフ
└── cmd/server/           エントリポイント：APIとフロントエンドを単一ポートで配信
```

## このプロジェクトを作った理由

実務でバックエンドシステムを構築・運用してきた経験は、GAFA級のインフラ面接や
本格的なML基盤職が実際に問うような「システムの基礎理解」——KVキャッシュが
何をなぜ改善するのか、アテンションがなぜFFN層と同じようにバッチ化できないのか、
量子化がなぜ無条件の高速化ではなくメモリ／計算量のトレードオフなのか——を
自動的には証明しません。このプロジェクトは、そうした基礎知識を「口で説明する
もの」ではなく「動かして検証できるもの」にするために作りました。このポート
フォリオの他プロジェクトと違い、意図的に特定の職務経歴の一文には紐づけて
いません。各要素が実際に何を証明しているかの深掘り版は`INTERVIEW_QA.md`を
参照してください。

## ライブデモ

[Render](https://render.com)の無料枠に`render.yaml`経由でデプロイしています。
ビルド時に`stories15M.bin`と`tokenizer.bin`を公式の公開ソースから直接
ダウンロードし（詳細は下記「モデルの重みについて」）、チェックサムを検証して
からビルドします。Dockerもクレジットカードも不要です。無料枠のサービスは
15分間アクセスがないとスリープするため、スリープ復帰後の最初のリクエストは
数秒かかります。

```bash
go run ./cmd/server   # weights/stories15M.bin と weights/tokenizer.bin を読み込む
# http://localhost:8080 を開く
```

**[inferlab-demo.onrender.com](https://inferlab-demo.onrender.com)**で
公開中。以下のベンチマーク数値は、その無料枠インスタンス
（共有CPU0.1コア、RAM 512MB）での実測値であり、見積もりではありません。

| 設定 | tokens/sec | no-cache比 |
|---|---|---|
| キャッシュなし (fp32) | 1.2 | — 基準 |
| KVキャッシュ (fp32) | 6.8 | 約5.6倍 |
| KVキャッシュ + int8 | 6.7 | 約5.5倍 |
| 逐次3件 (fp32) | 8.6（合計） | — |
| バッチ3件 (fp32) | 10.2（合計） | 逐次比+約19% |

この実測値には、安易な予測とは違う2点の発見があります。KVキャッシュの効果は
ローカル開発時よりもこの制限されたCPU上のほうがむしろ大きく出ています
（計算資源が乏しいほど再計算のコストがより重くのしかかるため）。そして
int8量子化はここではfp32よりはっきり速くもはっきり遅くもならず、ほぼ互角
でした——これは生のCPU速度ではなく「SIMDのint8命令パスがない」ことが決定
要因である、という説明と整合します（詳細は下記の設計上の判断と
`INTERVIEW_QA.ja.md`のQ6を参照）。

ローカル開発用には`dev-weights/`（.gitignore対象）にローカルコピーを置き、
`CHECKPOINT_PATH`/`TOKENIZER_PATH`で指定します。

```bash
CHECKPOINT_PATH=dev-weights/stories15M.bin TOKENIZER_PATH=dev-weights/tokenizer.bin go run ./cmd/server
```

## モデルの重みについて

重みファイルはこのリポジトリに**一切コミットしていません**。`render.yaml`の
`buildCommand`がビルド時に
[Hugging Face上のkarpathy/tinyllamas](https://huggingface.co/karpathy/tinyllamas)
（`stories15M.bin`）と[llama2.cリポジトリ](https://github.com/karpathy/llama2.c)
（`tokenizer.bin`）から直接取得し、ビルド前に固定のSHA-256チェックサムで検証
します。これによりチェックポイントの再配布に関するライセンス上のグレーゾーン
を完全に回避しつつ（本プロジェクトはKarpathy氏自身の公開リリースを参照する
だけで再配布はしていません）、gitリポジトリをバイナリなしに保てます。モデルの
重みはAndrej Karpathy氏がTinyStoriesデータセット
（[Eldan & Li, Microsoft Research](https://arxiv.org/abs/2305.07759)）で
学習したもので、本プロジェクトが自作しているのは推論エンジン部分のみです。

`go test ./...`はネットワークアクセスを一切必要としません。全パッケージの
テストは実際のチェックポイントではなく、小さく手組みした合成フィクスチャに
対して実行されます。

## 設計上の判断とトレードオフ

**デコード時のみのバッチ化、パディング・マスキングなし。** 位置に依存しない
線形層（QKVO射影、FFNのgate/up/down）は、アクティブな全シーケンスの現在
トークンの活性化を束ねて`Linear.BatchMatMul`を1回呼ぶ形でバッチ化しています
——共有の重み行列をレイヤーごとに1回だけメモリから読み出し、シーケンスごとに
毎回読み出す代わりにN個の内積に償却する、これがバッチ化の本質的なメモリ帯域
幅の恩恵です。アテンションはあえて単純なシーケンス・ヘッドごとのループのまま
にしています。各シーケンスはKVキャッシュの長さが異なり（continuous batching
では各シーケンスが生成の異なる時点でバッチに参入するため）、それを形状統一
するためのパディング・マスキングの仕組みはここには実装していません。これは
vLLMのような実システムが「バッチ化された線形代数パス」と「別立てのragged/
paged attentionカーネル」に分けているのと本質的に同じ構造を、小規模に忠実に
再現したものであり、正しさを犠牲にした簡略化ではありません。プリフィル
（初期プロンプトの処理）はシーケンスごとに逐次実行します。TinyStoriesの
プロンプトは短く、continuous batchingシステムがスループットの恩恵を最も
受けるのはそもそもデコード側だからです。

**`BatchMatMul`はタイル化・ブロック化されたGEMMではなく、N個の独立した行
単位の内積から始めています。** これは単一シーケンス用の`MatMul`を行ごとに
1回呼ぶのとビット単位で同一です（`internal/model`のバッチ化vs逐次の等価性
テストを参照）。そのおかげでこのテストは許容誤差ではなく*厳密な*一致で検証
できています。キャッシュブロック化版は正式なロードマップ項目です（後述の
既知の制限を参照）が、浮動小数点の加算順序を変えてしまうため、この厳密な
一致の保証を許容誤差ベースのものに置き換えることになります。

**行単位（出力チャネル単位）の対称int8重みオンリー量子化**を採用し、
GGUF方式のようなブロック単位・グループ単位の量子化は採用していません。
ブロック方式より実装・検証が単純でありながら、行列全体に単一のスケールを
使うより明らかに精度が高くなります——なぜそうなるかは`internal/tensor`の
外れ値行を使ったテストが実証しています。アクティベーションは一貫してfp32の
ままです（重みオンリー量子化）。`QuantMatMul`は別立てのint8アクティベーション
パスを必要とせず、各行のint8値をその場で逆量子化します。

**トークン埋め込みテーブルもAttention/FFNの重みと同様に量子化しています。**
TinyStoriesの規模では、フルサイズのLLMに比べて埋め込みテーブルが全パラメータ
に占める割合がはるかに大きくなります——`stories15M`の語彙数32,000・
`dim=288`の場合、埋め込みテーブルだけでモデル全体の約1500万パラメータ中、
約920万を占めます。行列演算の重みだけを量子化していたら、本来のメモリ削減
効果の大半を取りこぼしていたことになります。

**量子化はメモリを確実に削減しますが、本プロジェクト自身の計測では明確な
高速化にはなりませんでした——これはバグではなく、正直で妥当な結果です。**
`QuantMatMul`は要素ごとにスカラーの`int8 → float32`変換と乗算を行っており、
実ハードウェアがAVX-VNNIやARM NEONのドット積拡張命令などで提供するSIMDの
int8内積命令は使っていません。そうしたハードウェアパスがなければ、量子化
された乗算加算1回あたりのコストはむしろfp32版より高くなり、メモリ帯域幅の
節約が割に合うのはワークロードが実際に帯域幅律速である場合に限られます。
実際にRender無料枠の本番デプロイ（共有CPU0.1コア）で計測すると、int8は
fp32とほぼ互角でした（6.7 対 6.8 tok/s）——明確に速くも遅くもありません。
一方、より高速で専有されていないローカル開発マシンで計測すると、int8の
ほうが遅くなりました（13.3 対 17.7 tok/s）。どちらのハードウェアでも計算
オーバーヘッドは実在し目に見える形で現れますが、それが帯域幅の圧迫と
どうトレードオフするかはハードウェアによって異なる、というだけです。
ベンチマークパネルは「量子化は常に速い」という決めつけではなく、実ハード
ウェアで計測した結果をそのまま表示します。このトレードオフの詳細は
`INTERVIEW_QA.ja.md`を参照してください。

**モデルの重みはビルド時に取得し、リポジトリには一切コミットしていません**
——詳細は上記「モデルの重みについて」を参照。

**すべての単体テストは、実際の60MBチェックポイントではなく、小さく手組み
したフィクスチャに対して実行されます。** loader/tokenizerのテストは形式を
直接検証するために小さな合成ファイルを自前でシリアライズし、model/cache/
quant/batchのテストは小さなインメモリの`loader.Checkpoint`（レイヤー数は
数個、`dim`は一桁台）を組み立てます。これにより、テストスイート全体が
ネットワーク依存ゼロで1秒未満で完走します。`internal/model`のゴールデン
値テストはさらに、開発時に一度だけ実行した独立したNumPy再実装と出力を
突き合わせています——これは本プロジェクトで最も価値の高い正しさの検証
ゲートです。Transformerの数式に潜む微妙なバグは、そうしなければ「実モデル
の出力が支離滅裂に見える」という形でしか表面化せず、どの段階が壊れて
いるか特定する手立てがないためです。

## テストの実行

```bash
go test ./... -v
```

- `internal/tensor` — MatMul/RMSNorm/Softmax/SiLUを手計算・既知の参照値と
  比較。int8量子化・逆量子化の往復誤差が量子化ステップの半分以内に収まる
  ことを検証。行単位が行列全体単位より優れていることを示す外れ値行テスト。
- `internal/loader` — 手組みした合成チェックポイントに対するバイナリ形式
  パース。重み共有規約の両方の符号パターン。切り詰められた・壊れた入力が
  パニックではなく明確なエラーになること。
- `internal/tokenizer` — バイナリ形式パース。完全な貪欲BPEマージ
  アルゴリズムを通したエンコード→デコードの往復。生バイトフォールバック
  パス。BOS直後のスペース除去という仕様の癖。
- `internal/model` — 独立したNumPy参照実装と突き合わせたゴールデン値
  テスト。未来のキャッシュスロットに極端な値を仕込んで読まれないことを
  確認する因果マスキングの性質テスト。位置0でのRoPEが恒等変換になる
  こと。バッチ化vs逐次デコードの等価性（許容誤差でなく厳密一致）。
- `internal/cache` — キャッシュを使ったデコードが、毎ステップで完全な
  再計算と厳密に一致すること。独立した2つのシーケンスが決して混線しない
  こと。`max_seq_len`を超えた予約が明確にエラーになること。
- `internal/quant` — 量子化したチェックポイント全体のフォワードパスが
  fp32参照に近いこと。埋め込み行の逆量子化精度。量子化後の重みサイズが
  fp32より明確に小さいこと。
- `internal/batch` — Schedulerの`Admit`/`Tick`/`Evict`API自体が逐次
  `Step`呼び出しと同一の結果を出すこと。処理途中の退出・受け入れが他の
  進行中シーケンスを乱さないこと。容量制限が守られること。
- `internal/api` — プロンプト長・`maxTokens`・キャッシュなしベンチマーク
  脚のトークン予算に対するサーバー側クランプ。SSEストリームが`done`
  イベントを出すこと。ベンチマークエンドポイントが5設定すべてについて
  正の妥当な結果を返すこと。

## 既知の制限・ロードマップ

- **プリフィルのバッチ化なし、パディング・マスキングなし。** バッチ化される
  のはデコードフェーズのみです。意図的なスコープの切り出しである理由は
  上記「設計上の判断」を参照。
- **`BatchMatMul`はブロック化・タイル化されたGEMMではありません。** バッチ
  形状のAPIの内部はN個の独立した行単位の内積です。本物のキャッシュブロック
  化カーネルはさらなるスループット向上をもたらしますが、浮動小数点の加算
  順序を変えるため、バッチ化vs逐次テストは厳密一致から許容誤差ベースに
  変える必要があります。
- **量子化は行単位で、ブロック・グループ単位ではありません。** GGUF方式の
  ようなグループ化量子化（例：グループサイズ64）は、行ごとの管理コストと
  引き換えに同じビット幅でより高い精度を回復できます。
- **SIMDのint8内積命令パスなし。** これが本プロジェクト自身のCPUベンチ
  マークで量子化が高速化にならなかった直接の原因です——詳細は上記「設計上
  の判断」を参照。
- **`stories110M`はスコープ外です。** fp32だけでおよそ440MBあり、Go
  ランタイムやリクエストバッファを加えるとRender無料枠の512MBという
  システム全体のRAM予算に無理なく収まりません。`stories42M`
  （fp32で約165MB）は「もっと大きいモデルを試す」ためのビルド時パラメータ
  として文書化されています。`internal/loader`/`internal/model`はチェック
  ポイント自身のConfigヘッダーに対して汎用的に作られているためです。

## 各パッケージが証明していること

| パッケージ | 証明していること |
|---|---|
| `internal/tensor` | 正確でテスト済みの数値カーネル（行列積・正規化・活性化関数）、そして「行単位」を選んだ理由を裏付ける実際の精度の議論を伴う行単位対称int8量子化 |
| `internal/loader` | 重み共有の符号規約を含め、自己記述的でない実在のバイナリモデル形式を正しくパースする力 |
| `internal/tokenizer` | ライブラリではなく仕様書から、本番相当のBPEマージトークナイザーのアルゴリズム（バイトフォールバックやダミープレフィックスの癖まで含めて）を正確に再実装する力 |
| `internal/model` | 独立した参照実装と突き合わせて検証したゼロからのTransformerフォワードパス（RoPE・GQAアテンション・SwiGLU）、そして正しさに実際に関わる因果マスキング・バッチ化等価性という性質 |
| `internal/cache` | KVキャッシュが「なぜ」正しいのか（速いだけでなく結果が同一であること）を理解し、証明する力——多くの人が言葉では説明できても証明はできない部分 |
| `internal/quant` | チェックポイント全体に適用した重みオンリー量子化、そして小型モデルほど埋め込みテーブルがメモリ使用量を支配するという見落とされがちな事実への理解 |
| `internal/batch` | continuous batchingの本質的な構造——バッチ化できるもの（線形層）はバッチ化し、できないもの（raggedなアテンション）を偽装しない——そして無関係な進行中シーケンスを乱さないadmit/evictスケジューリング |
| `internal/api` | 推論エンジン全体を、このポートフォリオの他の公開デモと同じリクエストクランプの規律を持った、リソース制限付きの公開HTTPエンドポイントとして組み上げる力 |
